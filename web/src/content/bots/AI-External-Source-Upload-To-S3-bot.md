社内 AI に追加で読み込ませるデータファイルを、Slack で bot にメンションしてファイルを添付するだけで差し替えられる bot。
エンジニアに頼まなくても、経営層や営業層が自分で AI の振る舞いを更新できるようにした。

## 作ったきっかけ

社内AIは Amazon Bedrock で動いているが、追加のデータとしてS3に置いたファイルを参照している。
このファイルの更新は、エンジニアが都度 AWS コンソールを開いて、S3 の該当ファイルを手作業で差し替える必要があった。

AIの回答は、実際にAIを使う経営層や営業層に調整いただく必要が予想されたため、
非エンジニアでも自分で学習データを更新できるようにし、トライアンドエラーを加速させることを狙ってbotを作成した。

このbotはエンジニア同士のコンフリクト回避にも役立っていた。

## 構成

```
Slack（メンション + ファイル添付）
   │  Slack Events API
   ▼
AWS Lambda (Python) ── Slack からファイルをダウンロード ──▶ Amazon S3（所定のキーに上書き）
                                                              │
                                                              ▼
                                               Amazon Bedrock（External Source として S3 を参照）
```

| 要素 | 採用技術 | 理由 |
| --- | --- | --- |
| 受付 | Slack bot（Events API） | 社内で日常的に使っているツールなので、新しく覚える操作がない |
| 処理 | AWS Lambda (Python) | イベントが来たときだけ動けばよく、常駐サーバーが不要 |
| 保存先 | Amazon S3 | Bedrock がもともと参照しているファイルの置き場所 |
| AI | Amazon Bedrock | S3 上のファイルを External Source として参照 |

## 設計のポイント

### ファイルを置き換えるだけでAIが更新される仕組みに乗る

Bedrockでは、追加データをS3上のファイル名で指定し、External Source として参照している。
BedrockはリクエストのたびにS3のファイルを見に行くため、同じ名前のファイルを上書きするだけで、次の回答から AI に反映される。

そのためbotの責務は「Slack に添付されたファイルをS3の所定のキーへアップロードする」ことだけに集中でき、仕組みをシンプルに保っている。

### 更新履歴が Slack に残る

ファイルの更新が、必ず Slack 上のやり取りを経由するようになったことで、
その副次効果として、いつ・誰が・どのファイルに差し替えたかの履歴がSlackに残るようになった。
エンジニア自身が更新する場合も同じ経路を使うので、AWSコンソールでの手作業だったころより管理が楽になる副産物があった。

### 工夫した点・苦労した点

**インターフェースを差し替えられるよう拡張性を意識した作り**

社内では、エンジニア以外はSlackではなくLINE Worksを使用していた。
将来営業層がLINE Worksから学習データを更新する運用を前提とし、「メッセージを受けてファイルをS3に置く」部分を botとして独立させた。
受付側のインターフェースを差し替えるだけで、SlackにもLINE Worksにも対応できるようにした構成にしている。

**現在のファイルをダウンロードできるようにした**

アップロードだけでなく、今S3に置かれているファイルをbotからダウンロードする機能も用意。
更新する人はまず現行のファイルを取得し、それを編集してからアップロードすることができる。
古い手元のファイルで上書きして、他の人が加えた変更を消してしまう事故（デグレ）を起こしにくくすることにも繋がった。

## 今後の改善

現在の運用で必要な機能は揃っているため、今のところ大きな改善予定はない。
